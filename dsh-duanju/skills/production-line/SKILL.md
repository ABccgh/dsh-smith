## 一、核心原则：把「编」和「烧」分开

**凡是能用「读文件 + 比字符串」判定的东西，都不要用「生成一次看看」来判定。**

理由是量级落差，出处 `script-to-production:11-16`：实测一个镜头要重拍 **3–6 次**，
而 **720p/10s 一次 140 算力**、账号月产能 **725**。所以**编阶段的错**在烧阶段会被**乘性放大**。

**本 preset 的整条工序就是为了让所有能静态判定的错都在花钱之前暴露。**

### ⚠️ 一条反例，必须一起读（否则会把上面的原则用过头）

`script-to-production:70-82` 的 **R2** 说得比这条原则更硬：**闸门能判「道具引用错了」，判不了「这个故事不好看」**，
而且它明确写着 **「不要发明『爽点密度断言』去假装能测」**。

**于是「编与烧分离」的边界是**：它适用于**形状与引用**那一类错，**不适用于内容质量**。
内容只有两种判据 —— **平台评估**（见 `platform-submission`）与**人读**。**没有第三条。**

## 三、成本闸门：任何会花积分的动作之前，先报价、再获批

**协议全文在 `cost-gate`。** 这里只留本 preset 必须自己守住的部分：

### 三条不可让渡的

1. **不读余额，改读报价。** `dreamina user_credit` **实测会静默返回全 0 字段**，
   而同一时刻其他鉴权命令正常 —— 那条命令失效，**不是余量为 0**。
   **基于坏读数决定能否花钱，比不读它更危险。**（`cost-gate:12-14`、`:189-191`）
2. **报价 ≠ 授权。** `node quote` 返回的金额只是**上限**；**必须报给用户并得到明确批准**。
   标准三步：`node quote` → 报给用户等批准 → `node confirm --credit-ceiling <批准值>` → `node run --credit-token`。
   **报价超过上限时 `confirm` 不签发凭证 —— 那是硬闸门，不是提示。**（`cost-gate:21-38`）
3. **失败/退款要如实说。** `creditsAmount` 是**提交时预扣快照，不是最终净消费**；
   核销与退款都**不回写**它，**拿它求和会把已退款的失败生成也算成花费**。（`cost-gate:18-19`）

### 批量的硬闸门

```powershell
node D:\AIVideo\tools\batch.mjs run --jobs <jobs.jsonl> `
     --sample-ok --approved-ceiling <用户批准的总额>
```

- 未传 `--approved-ceiling` → **拒绝**，并把预计金额打印出来供你报价
- 预计 > 已批准 → **拒绝**
- 缺 `--sample-ok` → **拒绝**（必须先跑 1 条样例并**肉眼**确认风格对）

（`cost-gate:49-56`，逐条。）

### ⚠️ 单价必须说清「模型 + 分辨率 + 时长」三者

**只报时长会得到错误价格。** `cost-gate:91-113` 的阶梯表证明**模型是价格的独立维度**：
720p/10s 在 `seedance_2.0_vip` 是 **140**、在 `seedance_2.5` 是 **200** —— **两个都对，因为是两个模型**。

⚠️ **本工作台的两个积分基数是并存的，且没有任何文件调和过它们**（D-74，`PROJECT.md:113` 把这行列为
「会自己过期的读数」）：**725** 与 **745**。差 **20** 的成因**未解**，
且它是**唯一会改变「本月能做几条」结论的未解项**（`PROJECT.md:30-31`）。
**所以：报产能时必须写明你用哪一个基数、为什么。** 不要写一个裸数字。

**`D:\AIVideo\tools\script-gate.mjs:60-66` 的 `MEASURED_CREDITS`（5 条）缺「模型」这一维**，
与 `cost-gate` 的阶梯表**不矛盾但也不完整** —— 引用时优先用 `cost-gate` 那张带模型的表。
（详细对照见 `shotlist` 技能第八节。）

### 产能是比成本更硬的约束

`cost-gate:80-84`：**额度本身读不到**（两条通道都读不到，不是「这一条坏了」），
所以实际已用只能**累加 `node quote` 的报价**来近似 —— **先记账、后花钱**，不要花完再查。

现状档（69 元 / 725 积分）的实测推论（`cost-gate:126-140`）：
**30 秒成片约 434 积分、每周期勉强 1 条；60 秒做不到；1080p 原生做不到。**
**省下一次重试 = 一次生成的积分 + 相应的产能占比**，所以**提交前把提示词与参考图做足仍是最高回报动作**。

## 四、三条已实测的失败模式（**都会「看着 work」**）

逐字来自 `script-to-production:59-82`。**它们不会报错，所以只有在你知道该看哪里时才看得见。**

| # | 形态 | 为什么不会有人发现 | 检查 |
| --- | --- | --- | --- |
| **R1** | **账本落错产品线** | `batch.mjs:49` 的默认账本写死在 `products/image-to-video/manifest.json`。做短剧若不显式注入 `DSH_BATCH_MANIFEST`，**短剧的每一条支出都记进 image-to-video 的账本**，而汇总、报表、闸门**全部照常工作、不报错** | 显式传 `DSH_BATCH_MANIFEST`；曾有 `E10-账本归属` 断言 `manifest.seriesId` 与目录名一致（该断言所在的闸门范围已不在本 preset，见 `shotlist` 第十节） |
| **R2** | **全绿而片子不能用** | 闸门判不了「这个故事不好看」。**不要发明「爽点密度断言」去假装能测** | 花第一分钱之前，把正文与分镜表**用 `present` 交给用户读一遍**。**这是人的工作，不是脚本的工作** |
| **R3** | **文本层一致而像素层漂** | 闸门能断言「所有镜头引用同一套圣经资产」，但抓不到「同一张三视图生出来的两张首帧图其实不像」 | 出完首帧图后做一张联络表，**人工目视**比对角色是否同一人。**没有自动化替代** |

⚠️ **R3 与一条历史事故同族，值得一起记**：QC 生成的联络表 `_contact-sheet.png` 是 **1480×744 的横向拼图**，
被「取最新文件」逻辑当成了首帧，导致输出 **960×960（1:1）** 而不是 9:16。
**缺陷在选图逻辑，不在生成服务** —— 但它伪装成「服务不遵守比例」。
所以有一条硬纪律：**永不「取最新文件」**；素材只认「参考图」列里显式声明的文件名。

## 六、能力边界（不要越界声称）

来自 `script-to-production:84-94`，仍然成立，且**必须与「可观察验收」一起读**：

| 能 | 不能（必须人） |
| --- | --- |
| 比例与真实像素尺寸（`probe-video.mjs` 读 MP4 `tkhd`） | **动作是否自然连贯**（一帧看不出时间信息） |
| 人物跨镜头**是否同一人**（抽帧后比对发色/服装/脸） | **音频、节奏、卡点** |
| 构图、光影、是否崩坏 | **动态模糊是否可接受** |
| 分镜表的结构与引用合法性 | **剧情是否好看、钩子是否真的抓人** |

**抽帧复核验证的是单帧内容，验证不了动作连贯性与音频。不要把它说成「解除了看不到画面的限制」。**
