# 有戏AI：你能做到哪一步

## 一、一句话结论

**你能驱动平台边界这一侧的全部工作，不能驱动平台侧的任何一步。**

这个平台**没有 CLI、没有公开 API**（`/openapi.json` 与 `/swagger` 都 404；`docs.` / `open.` / `api.` / `developer.` 子域全 NXDOMAIN），
而且**本工作区里没有任何凭证** —— 实测：全树递归搜 `.env*` / `*token*` / `*cookie*` / `*credential*` / `*secret*` → **0 个文件**。

它的私有 app API 是可以从它的前端产物里枚举出来的，但**每一个调用都要从已登录浏览器的 `localStorage` 读 `token`**：

```js
// 前端原文
const n = localStorage.getItem("token") || "", d = localStorage.getItem("channel") || ""
headers: { "Content-Type": "application/json", token: n, channel: d }
```

**所以：不要声称你能生成、能评估、能投稿。** 那种声称会让用户以为流程在往前走，而实际上它在等一个人。

### ⚠️ 「平台评估」是**两次不同的评估**，不要把它们的条件混在一起

有戏AI 对同一部作品至少做**两次**评估，时点、读的东西、维度都不同。**这个区别以前没写在任何技能里**，
而它足够让一份按错条件准备的成果被打回：

| | **剧本评估**（写分镜之前） | **发行评估**（制作完成之后） |
| --- | --- | --- |
| 时点 | 剧本写完、投入生成之前 | 成片交付、申请**托管发行**时 |
| 平台读什么 | **正文**（`可导入-<剧名>-全N集.txt`）—— 分镜表它一个字都不读 | **成片**及相关发行资料 |
| 维度 | 五个量化维度（人设张力／情绪爽点／卡点悬念／叙事节奏／台词画面）＋ 评级 | **内容质量、制作完成度、题材适配度、版权清晰度** |
| 门槛 | 评级 ∈ `["S+","S","A+","A"]`（发布闸门，见第五节） | 「审核通过后，由有戏AI 统一对接渠道并推进上线」 |
| 谁判 | 平台（你在网页上点「立即发起评估」） | 平台 |

发行评估那**四个维度**逐字引自平台自己的《**有戏AI 托管发行及超创扶持计划**》（用户 2026-09-21 提供的 PDF，共 3 页；
**本机没有第二份副本，也没有与平台的活接口核对过**）。那份文件**没有**给出这四个维度的判据、阈值，也没说是否自动判定 ——
**只记它的原话，不要替它补规则。**

**托管发行的五步流程（同一份文件，逐字）**：
1. 提交作品申请：创作者提交成片及相关发行资料。
2. 平台评估：平台从内容质量、制作完成度、题材适配度、版权清晰度等维度进行审核。
3. 进入托管发行：审核通过后，由有戏AI 统一对接渠道并推进上线。
4. 发行优化与运营跟进：平台根据渠道规则优化标题、封面、文案及上线节奏。
5. 数据回收与收益结算：作品上线后持续跟踪表现，并按合作约定进行结算。

**两处可以直接行动的含义：**
① **「版权清晰度」是创作者侧的义务**，不是只能等平台告知的条件 —— 文件原文「创作者负责完成内容生产并**保证版权清晰**」。
它能提前准备（版权链、授权文件、素材来源），所以它**不同于** `market_fit.compliance_status` 那种「本地判不了」的平台侧事实。
② 第 4 步说平台会改**标题、封面、文案** —— 所以这些**不是**必须定稿的交付物，别把它们当成要锁死的东西。

### 托管发行与超创扶持：平台自己给出的数字（同文件，逐字，**未与平台二次核对**）

- **分成**：标准托管发行模式下 **创作者 70% / 有戏AI 30%**。
- **分工**：创作者负责完成内容生产并保证版权清晰；有戏AI 负责发行渠道对接、包装优化、上线推进、运营协同和结算跟进。
- **渠道**：文件称覆盖海内外超过 **12+** 短剧与内容平台，已列名海外 **TikTok / YouTube**，
  国内 **抖音红果 / 腾讯视频号 / 火龙漫剧 / 快手**。
- **海外**：文件称「海外 CPM 是国内的数倍」—— **没有给数字**，所以不许拿它做任何算术。
- **超创特权**（进入「超级创作者」扶持后）：剧本支持（平台直接提供剧本或选题共创）、
  **算力支持 —— 原文「针对重点项目由平台提供最高100%算力支持，创作者无需负担算力成本」**、
  联合发行支持、选题支持、专项合作机会。文件同时写明最终能否进入由平台综合评估，
  且四条准入特征里的任何一条**都不是承诺**。

> **这一小节为什么放在生产 preset 里：算力是钱。** 「最高 100% 算力支持」与 `script-delivery` 的成本纪律
> 直接相关 —— 它意味着**重点项目的算力成本可能不在你身上**。所以报价或排期之前，
> **先问用户这一部是否在扶持范围内**，不要默认按自付算力算。文件里没有判据，**只有用户能回答**。

## 二、只能由人做的六步，以及每一步的「智能体侧替代产物」

| # | 只有人在网页上能做 | 你交付什么，让这一步最短 |
| --- | --- | --- |
| 1 | **登录**（手机号/验证码） | 无需产物；流程的输入不依赖登录态 |
| 2 | **剧本粘贴**（纯文本 textarea，**没有文件上传**） | `script\可导入-<剧名>-全N集.txt` —— 已过 E9（分集标记统一、连续、首集为 1、单集 ≤2 000 字） |
| 3 | **分镜表导入**（**文件上传，只认 `.xlsx` / `.xls`**） | `storyboards\第NN_15列_平台导入.xlsx`，由 `board-to-xlsx.mjs` 产出并**回读自证** |
| 4 | **「生成故事板」/「生成剧集」**（消耗平台算力） | 报价与产能口径（见第四节）；**不许据档位报价** |
| 5 | **「立即发起评估」**（零剧集时按钮无效） | 一个提示：这一步要求先生成剧集 |
| 6 | **发布表单填写与提交** | 一份填表清单（字段与上限见第五节）；提交仍需人做 |

**另有一个不是步骤但只有人能拿到的读数**：`compliance_status` 与 `popularity_status`。
平台自己的措辞是「未见可据此直接判定阻断的明确材料」—— **那不是通过，也不是阻断，是没有结论**，
而它比评级更硬（发布前置）。**不许把它读成通过。**

顺带一条同族的：`@[主体]` 在**旁白模式**下是否真的绑定静态画面主体，**本项目没有测过**（`PROJECT.md:670`）。不要断言。

## 三、导入格式（读自前端产物与官方模板，逐字）

### 剧本：粘贴，不传文件

> 请导入剧本，将为你自动分集（文本请用"第n章/集"分割）
> 剧本支持10万字以内，长剧本需要分集，**每一集必需控制在2000字以内**
> **注意：不能混合使用**，比如在同一个剧本中，同时使用：第1章， 第2集 ，这样是不能分集的

### 分镜表：文件上传，只认 Excel

前端原文的校验：`仅支持 Excel 格式（.xlsx / .xls）`。
**本地表是 CSV，必须先导出成 xlsx**，导出工具是 `board-to-xlsx.mjs`（见 `drama-workspace` 技能）。

### 三份官方模板的真实表头

⚠️ **前两行是注释行，导入前必须删除，第 3 行才是表头。** 模板第 1 行原文：
「注意事项：此模板的第1，2行是注释行，导入分镜模板前，请将前两行删除」。

| 模板文件 | 列数 | 第 3 行表头（逐字） |
| --- | --- | --- |
| `分镜模板_剧情_生图转视频.xlsx` | **15** | 镜头 镜头剧本 分镜号 景别 构图 运镜 光影 场景 站位 分镜描述 音效 对白 时长 镜头图片提示词 镜头视频提示词 |
| `分镜模板_剧情_参考生视频.xlsx` | **13** | 镜头 镜头剧本 分镜号 景别 构图 运镜 光影 场景 分镜描述 音效 对白 时长 镜头视频提示词 |
| `分镜模板_旁白.xlsx` | **6** | 分镜号 分镜剧本 场景 对白 分镜图提示词 分镜视频提示词 |

- **「参考生视频」删掉的是 `站位` 与 `镜头图片提示词` 两列** —— `分镜描述` **在**，这个模式本来就没有图片提示词列。
  这张表被改错过一次而且**方向是反的**，所以写在这里：`shotlist` 技能前身先写对了，随后「更正」错了。
  **权威是解出来的 xlsx 本身**，`board-to-xlsx.mjs` 的表头数组是照它抄的。
- 「旁白」模式 **没有 `时长` 列**；它的第 4 列注释原文：`（选填，空则是空镜，非空指定旁白或角色说话)`。
- 必填列（第 2 行注释）：第 1 列 `(必填，生成分镜视频的单元)`、第 3 列 `(必填，分镜号，改模式下和镜头一一对应)`。
- **`分镜模板_旁白.xlsx` 与 `shot_import.xlsx` 是同一个文件**（逐字节相同，11 909 B）；后者是平台自己的下载文件名。
- 参考主体格式：`@[主体]`，例如 `@[凌霄]`、`@[八卦炉]`、`@[兜率宫内-八卦炉区]`。
- **我们采用「使用方式一」**：只填分镜信息，让平台生成提示词列 —— 那些列里有平台自己的 Shot 语法与主体替换逻辑，自己拼只会更差。

## 四、成本：**档位不构成报价**

平台官方教程给出的产能口径含抽卡，是**档位区间**：`133 / 255 / 400 / 500 / 3000 / 4420`（算力/分钟）。

**133 → 4420 是 33 倍。** 所以这组数字**不构成任何报价依据**；在这种场合说「未测量」，不要挑一个档位算出一个数。
本机也**没有**任何可用的余额读数源可以求差值。

## 五、发布闸门：**六条**，不是三条

逐字读自平台前端产物（发布按钮的处理函数）：

```js
if (mt(a.creationDetail)) { we.warning("该剧本已提交发布，请勿重复提交"); return }
const o = a.episodeList.length > 0;
if (a.episodeList.length < 10) { we.warning("剧集少于10集，不能发布"); return }
const s = a.creationDetail?.review_status === "completed";
if (!o && !s) { we.warning("请先生成剧集，或者先评估剧本"); return }
if (!o) { we.warning("请先生成剧集后再发布"); return }
if (!s) { we.warning("请先评估剧本后再发布"); return }
// …取 export_data，算出等级
if (!["S+","S","A+","A"].includes(xe)) { we.warning("只能发布A级以上评级的剧本"); return }
```

**六条**：① 重复提交 ② `<10 集` ③ 未生成且未评估 ④ 未生成 ⑤ 未评估 ⑥ 评级 ∉ `["S+","S","A+","A"]`。

评级映射（同一文件）：`>=95 S+ / >=90 S / >=85 A+ / >=80 A / >=70 B / >=60 C / 否则 D`。

### 仓库从未记录的第二道闸门：发布表单自身

同一文件里还有五条，**本地文档里没有**：

| 条件 | 提示原文 |
| --- | --- |
| 卖点 < 5 字 | 「请填写一句话卖点（至少5字）」 |
| 简介 < 10 字 | 「请填写剧本简介（至少10字）」 |
| 未填目标受众 | 「请填写目标受众」 |
| 售价为空或 ≤0 | 「请输入有效的售价」 |
| 未上传封面 | 「请上传封面」/「请先生成AI封面」 |

字段上限：**卖点 120**、**简介 500**。
提交体：`{title, core_selling_point, overall_comment, audience_profile, gold_coin, tags, cover_item_id}`。

### 一条「仓库比平台更严」的差异，方向很重要

仓库把「所有剧集**已生成**」当硬闸门，而平台源码只测 `episodeList.length > 0`（**存在**，不是生成状态）。
**仓库版更严，所以它不会产生假绿** —— 但引用时要说清这是仓库读数，不是平台判据。

## 六、评估报告：你写什么、它返回什么

**你写进去的**（`products\<剧名>\评估报告-回填.json`）：

```jsonc
{
  "readings": [
    {
      "评估时间": "…",
      "overall_score": 82.6,
      "grade": "A",
      "quantitative_scores": [
        { "id": "characterization",    "name": "人设张力", "score": 8.5 },
        { "id": "emotion_payoff",      "name": "情绪爽点", "score": 7.9 },
        { "id": "suspense_retention",  "name": "卡点悬念", "score": 8.6 },
        { "id": "narrative_pacing",    "name": "叙事节奏", "score": 7.7 },
        { "id": "dialogue_visuals",    "name": "台词画面", "score": 8.8 }
      ],
      "market_fit": { "compliance_status": "…", "popularity_status": "…" },
      "script_quality_md": "…",
      "potential_risks_md": "…"
    }
  ]
}
```

**它返回的字段**：`review_report.overview.{overall_score, grade}`、
`quantitative_scores[]`（五个 id 就是上表那五个）、`market_fit.{compliance_status, popularity_status}`、
`script_quality_md`（诊断正文）、`potential_risks_md`、`export_data`。

### 三个读数陷阱

1. **渲染出来的报告不是真实判决的证据。** 前端有硬编码兜底值（人设张力 85 / 情绪 78 / 卡点悬念 82 / 叙事节奏 88 / 画面 84），
   并且容忍两种刻度：`return N > 0 && N <= 10 ? N * 10 : N`。读到什么就写什么，不要替它换算。
2. **`reviews/full_script_review` 不是端点。** 本仓库在 4 处把它当「评分接口」引用过，而它在平台产物里
   **只作为文件路径子串出现 3 次**（用于决定是否打开评估菜单）。真实路径是
   `POST /api/drama/drama-creation/{id}/review/start`（**无请求体**）、`GET …/review-report`、`GET …/review-export`。
   **不要引用那个不存在的接口。**
3. **「只给分不给诊断」是常态。** 本项目第二次读数平台只给了分、没给新的诊断文字，
   所以「现在还差在哪」**没有权威答案**。如实说，不要自己编一份诊断。

## 七、读数回来了怎么处理

见 `script-delivery` 技能第五节（追加 `readings[]` → 跑 `E19b` → 报差值 → **标注证据等级**）。
一句话：**它是用户的转述，不是本机的实测**，写的时候把这一层说出来。
